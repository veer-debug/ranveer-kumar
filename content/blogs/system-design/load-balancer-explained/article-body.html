Load Balancer Explained: The Traffic Police of the Internet

Imagine millions of users hitting your app at once. If every request lands on one server, that server dies. A load balancer sits in the middle and spreads traffic across many backends.

Ranveer Kumar · Backend Engineer & System Design Enthusiast

A load balancer distributes incoming requests across multiple servers so no single machine gets overloaded. It is one of the first things you add when a system needs to scale beyond one box.

Think of a supermarket: one cashier means a long queue. Several cashiers with someone directing customers to the shortest line keeps things moving. That director is the load balancer.

Why do we need a load balancer?

Without a load balancer
  • ✗ One server becomes overloaded
  • ✗ High latency and failed requests
  • ✗ Downtime when traffic spikes
  • ✗ Hard to scale horizontally
With a load balancer
  • ✓ Traffic spread evenly
  • ✓ Better performance under load
  • ✓ High availability
  • ✓ Fault tolerance and easier scale-out

Basic architecture

The load balancer picks which backend handles each request. If one server fails, health checks remove it from the pool and traffic goes only to healthy machines.

Layer 4 vs Layer 7

Layer 4 (Transport)
  • → Routes by IP and TCP/UDP port
  • → Fast — does not inspect HTTP body
  • → AWS NLB, HAProxy in TCP mode
  • → Gaming, streaming, raw throughput
Layer 7 (Application)
  • → Routes by URL, headers, cookies
  • → Smarter path-based routing
  • → NGINX, AWS ALB, Envoy
  • → APIs, microservices, web apps

At Layer 7 you can send /api/users to the user service and /api/payments to the payment service — same load balancer, different backends.

Load balancing algorithms

Round Robin
Requests go to each server in order: Server1, Server2, Server3, then back to Server1. Simple and common.
Default choice
Least Connections
Traffic goes to the server with the fewest active connections. Better when some requests take longer than others.
Variable workload
Weighted Round Robin
Stronger machines get more traffic. If Server1 has weight 5 and Server2 has weight 2, Server1 receives more requests.
Mixed capacity
IP Hash
The same client IP always hits the same server. Useful for session stickiness and caching.
Session affinity

Health checks and sticky sessions

Load balancers ping backends on an interval. If a server stops responding, it is removed from rotation until it recovers. Users keep getting served by healthy nodes only.

Sticky sessions pin a user to one server — helpful for shopping carts or in-memory login state. Too much stickiness hurts even load and makes scaling harder; Redis or stateless APIs are usually better at scale.

Reverse proxy vs load balancer

Reverse proxy
  • → Sits in front of servers
  • → Hides backend infrastructure
  • → Can cache and compress responses
Load balancer
  • → Main job is distributing traffic
  • → Focus on availability and scale

NGINX, Envoy, and HAProxy can act as both. In practice the line blurs — what matters is whether you need routing, TLS termination, caching, or pure distribution.

Hardware vs software

Hardware
  • ✓ Very high throughput (e.g. F5 BIG-IP)
  • ✗ Expensive appliances
Software
  • ✓ NGINX, HAProxy, Envoy
  • ✓ Cheap, flexible, cloud-native

Global load balancing and Kubernetes

For users worldwide, global load balancing sends traffic to the nearest region — India to Mumbai, US to Virginia, Europe to Frankfurt — so latency stays low.

In microservices, traffic often flows: Client → API Gateway → Load Balancer → services. In Kubernetes, a Service load-balances across pods; Ingress adds Layer 7 path rules like /api → backend-api.

Challenges with load balancing

Load balancers solve real problems, but they introduce their own. These are the ones that show up in production and in interviews.

01
Single point of failure
If the load balancer itself goes down, everything behind it is unreachable. Run paired LBs with failover.
02
Session management
Sticky sessions do not scale well. Prefer shared session stores (Redis) or stateless services.
03
Uneven traffic
Some requests are heavier than others. Round robin alone may not be enough — use least connections.
04
Misconfigured health checks
Too aggressive checks mark healthy servers as down; too loose checks send traffic to broken nodes.

"A load balancer is only as good as your health checks and your capacity planning behind it."

Interview questions

Difference between Layer 4 and Layer 7?
L4 works on TCP/UDP (IP + port). L7 understands HTTP — URL, headers, cookies — and can route intelligently.
What happens if a server dies?
Health checks detect failure and remove that server from the pool. Traffic flows only to healthy backends.
Why are sticky sessions bad sometimes?
They reduce even distribution and make horizontal scaling harder when state lives on one machine.
The bottom line

A load balancer is not optional once you run more than one server. Without it, scaling is painful and one failure takes down the whole path.

With it, you get even distribution, failover, and room to grow. Every large system — from e-commerce to streaming — relies on load balancing behind the scenes.
